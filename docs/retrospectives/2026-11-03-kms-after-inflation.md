## RCA

### P-02：issue のコメントの数値が出力と違う（2 回目）

- なぜ 1：コメントの数値を、出力を見直さずに書いた。
- なぜ 2：出力を読んだときの印象（「ほぼ 1e-6」「1e-4 くらい」）を、そのまま上限として書いた。
- なぜ 3：数値を出典に結びつける手順（メモリ「ノートの数値は出典つきで」）が、ノートだけを対象にしていた。issue のコメントは報告として軽く扱い、照合の対象から外れていた。
- 根本原因：公開する文章のうち、ノート以外（issue、PR、報告）には、数値を出力と照らす手順がなかった。
- 同じ根から、リポジトリの URL についての主張（P-06）も確かめずに報告した。
- 再発防止策：メモリ「ノートの数値は出典つきで」の対象を、issue、PR、ユーザーへの報告にも広げる。上限を書くときは、出力の最大値を切り上げた値を書く。

### P-01：積み重ねた PR の base を消した

- なぜ 1：#84 を `--delete-branch` 付きでマージし、#86 の base が消えた。
- なぜ 2：base のブランチが消えると、GitHub が依存する PR を main に付け替えてくれると思い込んでいた。このリポジトリでは付け替えられず、#86 は閉じた。
- なぜ 3：積み重ねた PR をマージする手順が、リポジトリにも手元にも書かれていなかった。
- 根本原因：積み重ねた PR をマージする手順がなかった。
- 再発防止策：CONTRIBUTING.md に手順を書く。下の PR をブランチを消さずにマージし、上の PR の base を main に付け替えてから、ブランチを消す。

### P-03：rebase の衝突のあとビルドしなかった

- なぜ 1：衝突を解いたあと、すぐに `git rebase --continue` した。
- なぜ 2：衝突の印を消せば終わりだと考え、解いた結果がコンパイルできるかを確かめる段階を置いていなかった。
- 根本原因：衝突を解いたあとに、ビルドで確かめる手順がなかった。
- 再発防止策：CONTRIBUTING.md に、衝突を解いたら `cargo build` と変更したファイルの差分を確かめてから続ける、と書く。
